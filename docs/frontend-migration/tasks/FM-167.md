# FM-167: Let The Caps Check Be Left, And Show How Far It Has Got

Status: planned Owner:

## Outcome

The longest blocking interaction in the app stops being a trap. `CapsCheckDialog.tsx` sets `disableEscapeKeyDown`
(`:136`), renders no button at all (`DialogActions` at `:173-177` holds only explanatory text), shows an indeterminate
spinner (`:166`), and re-renders the whole message list every 500ms inside `aria-live="polite"` (`:146-159`), so a
screen reader re-reads every line each tick. A bulk recheck across dozens of indexers locks the config tab for minutes
with no exit and no sense of progress. Verified backend constraint: there is no cancellation. `IndexerWeb.java:59`'s
`POST /internalapi/indexer/checkCaps` is synchronous over `IndexerChecker`'s `executor.invokeAll` (`:377`), no abort
endpoint exists, and `CheckCapsResponse` carries no counters — so this packet is client-side only: leaving means the
user stops waiting, and progress is derived from which indexers have reported. Exit, progress, and the announcement fix
are the same dialog's waiting experience.

## Acceptance

- The dialog offers one clearly worded exit — a button in `DialogActions` and the `Escape` key running the same path —
  whose label and adjacent text say plainly that the check continues on the server and only the waiting stops. Backdrop
  clicks still do not dismiss it, so a long check is not lost to a stray click.
- Leaving is safe under the FM-083 pattern: polling stops, and the eventual resolve or reject of the abandoned
  `checkCaps` request writes nothing — no form write-back, no toast, no reopened dialog — proven by a test that resolves
  the abandoned promise after the dialog closed, and by one that starts a second check first.
- While a check runs the dialog reports "n of m" — m the indexers it submitted, n the distinct indexers that have
  reported at least one message — with a determinate indicator. Because the map proves reporting rather than
  completion, the wording says so and a `F-CONFIG-INDEXERS` gap line records that the backend exposes no completion
  counter. The single-indexer case (m = 1) still reads sensibly and gains no noise.
- Announcements append instead of repeating: the visible list is no longer itself a live region, and a polite live
  region announces only lines that arrived since the last tick plus progress changes. List items use stable keys so
  rendered lines are not remounted every 500ms. A test drives two poll ticks and asserts the live region holds only the
  new lines, not the accumulated list.
- The visible list keeps its `config-indexer-caps-messages` testid, order, and content, so existing unit and system
  assertions still address it.
- `config-indexers.spec.ts` keeps every existing caps assertion and gains one that opens a bulk recheck, reads the
  progress text, leaves the dialog, and finds the config tab usable — the point of the packet, against the real backend.
- Screenshot strip per `../README.md` *Visual Gate*: the dialog mid-check with progress and messages, the dialog for a
  single indexer, and the config tab immediately after leaving a running check — 1280x800 and 390x844.
