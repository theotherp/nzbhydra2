deterministic order: top to bottom, stopping after the first whole-string (`matchAll`) mapping applied, replacing today's

## Acceptance

- `CustomQueryAndTitleMapping` gains `String name` (null), `boolean enabled = true`, `List<String> examples = new
  ArrayList<>()`, with no migration step and no `configVersion` bump: a deserialization test over content lacking all three
  keys proves an older config loads enabled and example-less.
- Relevant-mapping filtering separates the directions: for `RESULT_TITLE` metadata only `affectedValue == RESULT_TITLE`
  mappings are relevant; for a search request only `affectedValue != RESULT_TITLE` ones whose `searchType` matches; a
  mapping with `enabled == false` never is. The list then applies in order and stops after the first applied `matchAll`
  mapping, logged at debug under `LoggingMarkers.CUSTOM_MAPPING`; the multiple-matchAll error branch is gone.
- Handler tests, each red before the change: first of two matching whole-string mappings wins; a partial before a
  whole-string one is applied too; a partial after an applied whole-string one is not; a disabled mapping is skipped; a
  `TITLE` mapping does not reach a result title, nor a `RESULT_TITLE` mapping a request.
- The endpoint takes `{mappings, mappingIndex, examples}` and answers `{results: [{input, thisMapping: {match, output,
  error}, chain: {output, appliedIndices, error}}]}`. `mappingIndex` is a boxed `Integer`: absent or negative means chain
  only — a primitive `int` would default to 0 under ADR-0018 and silently test the first mapping. The chain forces
  `affectedValue = QUERY`, season 1, episode 2 as the single-mapping test does today, ignoring each mapping's own
  `affectedValue`; over 200 example lines is answered HTTP 400 unevaluated. An endpoint test asserts, for several examples
  through a two-mapping chain, each line's `thisMapping` match and output, chain output and `appliedIndices` (into the
  request's `mappings`, not the filtered list); plus the cap and a broken `from` reaching `error`, not HTTP 500.
- `SearchingConfigValidator` keeps the regex check over every mapping, disabled included, and adds a *warning* (not an
  error) naming both when two enabled `matchAll` mappings share an identical `from`; both tested.

## Handoff

### Outcome

Custom query/title mappings are nameable, individually disableable and carry saved example inputs, all three added
without a migration step or a `configVersion` bump. Mapping evaluation now separates the two directions and is
deterministic: relevant mappings apply top to bottom and no mapping applies after the first applied whole-string
(`matchAll`) mapping; the old "two whole-string mappings match -> log an error and apply none" branch is gone. A `TITLE`
mapping can no longer reach a result title and a `RESULT_TITLE` mapping can no longer reach a search request — the
cross-application the stop rule would otherwise have made actively harmful. `POST /internalapi/customMapping/test` is a
batch at the same URL: many example lines against the whole edited list, answering per line for the edited mapping and
for the chain. `SearchingConfigValidator` still checks the regex of every mapping (disabled ones and result-title ones
included, which it silently skipped before) and adds a warning when two enabled whole-string mappings share an input
pattern.

### Decisions, Assumptions, Debt

- Dependency additions/changes: None.
- The test endpoint evaluates every mapping as if its `affectedValue` were `QUERY` *and* its `searchType` matched, the
  way the single-mapping test forced `affectedValue` before. The packet fixes only the `affectedValue`; leaving
  `searchType` honest would have made the chain silently apply nothing for a user whose mappings are all `TVSEARCH`,
  which is a worse answer to "what do my mappings do to this line" than today's behavior. Recorded as a normalization in
  the `API-CONFIG-CUSTOM-MAPPING-TEST` note.
- `thisMapping` answers for the mapping being edited even when that mapping is disabled — the editor asks what the
  pattern does, not whether it is live — while `chain` skips it, so the two answers can differ for a disabled mapping.
  Covered by `shouldSkipDisabledMappingsInChain` and recorded in the `APIS.yaml` note.
- The chain keeps the pre-existing structure in which relevance (and therefore matching) is decided once, up front,
  against the value as it arrives, not re-decided after each applied mapping. The packet's implementer prompt names this
  ("entries in `relevantMappings` have already matched"), so a mapping whose match was created or destroyed by an
  earlier mapping in the same run behaves as it did before this task.
- `warnAboutDuplicateWholeStringMappings` compares `from` literally. Two enabled whole-string mappings that are
  equivalent but not identical (`a.*` and `a.+`) are not warned about; nothing in the repository can decide regex
  equivalence.
- Assumption from repository evidence: `ResponseStatusException(BAD_REQUEST)` is how the example cap is answered, so the
  response type stays `TestResponse` and the generated schema stays clean; `ErrorHandler`/`ControllerAdvices` leave it to
  Spring's own handling.
- Temporary workarounds: None.
- Deviations from legacy behavior, each one recorded in a registry anchor:
  - The multiple-whole-string-mapping error branch is replaced by first-match-wins with a stop rule
    (`docs/frontend-migration/STATUS.md` Review entry for FM-194; changelog `note` below).
  - A `TITLE` mapping no longer reaches result titles and a `RESULT_TITLE` mapping no longer reaches search requests
    (`STATUS.md` Review entry for FM-194; changelog `fix` below).
  - The single-mapping test contract is replaced by the batch contract at the same URL
    (`docs/frontend-migration/APIS.yaml:45`, `API-CONFIG-CUSTOM-MAPPING-TEST`).
  - A broken or null `from` in a tested mapping is answered as a per-line `error` instead of HTTP 500
    (`docs/frontend-migration/APIS.yaml:45`).
  - `SearchingConfigValidator` now also checks the regex of disabled and `RESULT_TITLE` mappings, which its
    `mapSearchRequest` round trip skipped before (`STATUS.md` Review entry for FM-194).
