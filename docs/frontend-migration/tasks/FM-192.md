### Decisions, Assumptions, Debt

- Dependency changes: none.
- `STICKY_BACKGROUND` is the one constant with two consumers after the split, so it could not "move to its sole
  consumer". It is exported from `ResultsToolbar.tsx` and imported by `ResultsTable.tsx` rather than restated as a
  second `"background.default"` literal or lifted into a per-feature style module, which ADR-0014 forbids — and
  `SearchResults.tsx` could not hold it either, since Acceptance keeps that module's export list at one component.
- Deliberate deviation from the packet's "changing any dependency array" exclusion, one bullet per array, each forced
  by a hook boundary and each provably inert:
  - `toggleRefineSurface`'s `useCallback` now lists `setSidebarCollapsed` alongside `refineSurfaceCompact`. The setter
    comes from `useResultDisplayChoices` instead of a `useState` call `react-hooks/exhaustive-deps` can see, and a
    `useState` setter is referentially stable, so the callback's identity still changes only with
    `refineSurfaceCompact`. Nothing it reaches is memoized in any case: of this feature's components only `ResultRow` is
    wrapped in `memo`, and `DisplayOptionsMenu` — the only consumer — is not.
  - the pruning effect now lists `setSelected` alongside `filteredResults`, for the same reason and with the same
    consequence: it still re-runs exactly when `filteredResults` changes.
  The alternative in either case was an `eslint-disable`, which *Verification Integrity* forbids.
- Parts of the selection cluster stayed in `SearchResults`, each of them a lint finding that only appears once the
  code is in a `use*` function — the React-compiler-backed rules evidently bail out on `SearchResults` itself, so they
  are silent there at the baseline and fire on the extracted hook:
  - the two render-time ref writes (`visibleResultsRef.current = visibleResults`, `lastSelectedIdRef.current =
    lastSelectedId`) trip `react-hooks/refs`. The hook creates both refs — so its callbacks keep their empty dependency
    arrays and their stable identities, which `ResultRow`'s `memo` depends on — and returns them for the caller to
    write during its own render, which is exactly where those two assignments already were. The repository's other
    answer to this rule (`CapsCheckDialog.tsx:252`) writes the refs in an effect instead; that changes *when* the
    shift-click anchor and the visible-row list are written, which a pure-motion task must not do.
  - the pruning effect trips `react-hooks/set-state-in-effect`, and its `setSelected` call is not incidental — the
    bail-out-on-no-change return is the whole point of it (see its own comment). It stays in `SearchResults` and calls
    the hook's `setSelected`, which is the same shape the packet blesses for the persistence effect.
- The persistence effect did *not* need that exemption: all ten values it writes are in `useResultDisplayChoices`, so
  the single ADR-0054 write moved there whole, with base's key set, base's `satisfies StoredChoices`, and base's
  dependency array.
- Comments moved verbatim with their code, including two that now name something in a different file: the FM-055 note
  in `ResultsAlerts` refers to `hasRejectedResults` "above" (it is in `SearchResults`), and the `selectedResults` note
  in `useResultSelection` refers to "the window virtualizer below" (likewise). Rewording them would have broken the
  byte-identity of the runs they sit in; they are listed under Follow-Up Work instead.
- Assumption from repository evidence: `ResultsTable` is not wrapped in `memo` (nor is any other new component), so the
  four style memos it now owns behave exactly as they did in the parent — it re-renders with `SearchResults` on every
  scroll frame and the memos hold on unchanged dependencies. Adding a `memo` wrapper is explicitly Out Of Scope.
- Debt: none introduced. The prop lists of `ResultsToolbar` and `ResultsTable` are long by construction — the regions
  read that much of the pipeline's state, and threading it explicitly is what keeps the render identical.
