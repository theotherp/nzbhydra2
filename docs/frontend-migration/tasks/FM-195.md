## Outcome

Custom mappings leave the advanced fieldset at the foot of Searching for their own configuration tab at
`/config/customMappings`, where a mapping can be named, switched off and reordered, and is kept together with the example
inputs it was written for: the example field becomes multi-line and is saved with the mapping, and testing runs every line
through FM-194's batch endpoint, showing per line what this mapping and what the whole chain do. The React half of issue
#902, at the owner's 2026-09-13 request to split it by layer against `tasks/README.md`'s "never split by layer" rule.

## Outcome

Custom mappings have their own configuration tab at `/config/customMappings`. `CONFIG_TABS` carries a ninth segment
directly after `searching`, `ConfigNav` gives it a `SwapHoriz` icon, and `routes.tsx` mounts a lazy

them and, with the section gone, its `transport` prop.

"Match whole string", and a `multiline` example field bound to the mapping and saved with it; Test sends FM-194's batch
request — the whole edited list, unsaved edits to other entries included, at an index that is always inside that list —
and renders one table row per example line with this mapping's answer, the chain's answer and which mappings applied.

The persisted path did not move: mappings are still `searching.customMappings`, the anchor is still
`config-repeat-searching-customMappings`, and the save payload is unchanged.

## Decisions, Assumptions, Debt

- Dependency additions/changes: None.
- Assumptions: FM-194's `CustomQueryAndTitleMapping.enabled` initializes to `true`, so an entry with no `enabled` key is
  read as enabled (`CustomQueryAndTitleMapping.java`, and `openapi.ts`'s optional `enabled?: boolean`).
- Temporary workarounds: None.
- Deviations from legacy behaviour, each also recorded in the registry:
  - The example field is multi-line and is **saved with the mapping**; legacy's was a single throwaway line. The testid
    `config-custom-mapping-exampleInput` is retired for `config-custom-mapping-examples`
    (`FEATURES.yaml` `F-CONFIG-SEARCHING.selectors`).
  - The single-valued `config-custom-mapping-result` field is retired for `config-custom-mapping-results`, a table with
    one `config-custom-mapping-result-<line index>` row per line. The packet names only the example field as "the one
    testid this packet replaces", but the result field cannot survive the acceptance criterion that replaces it with a
    per-line table; both retirements are recorded together in `FEATURES.yaml` `F-CONFIG-SEARCHING.selectors`.
  - A whole-request refusal (no example lines, no input pattern, over the endpoint's 200-line limit, or a failed
    request) is an `Alert` at `config-custom-mapping-error` rather than text in the old Result field
    (`FEATURES.yaml` `F-CONFIG-SEARCHING.selectors`).
  - FM-131's advanced wrapper around the section is gone with the move, and with it
    `config-advanced-expander-custom mappings…` and `config-fieldset-custom mappings…`
    (`FEATURES.yaml` `F-CONFIG-SEARCHING.selectors`, `COMPONENTS.yaml` `C-CONFIG-FIELDS`).
  - The settings-index entry's `help` prose was corrected from "Rewrite result titles before they are processed…" to
    name queries and search titles too, which is what the mapping list actually does
    (`COMPONENTS.yaml` `C-CONFIG-SETTINGS-INDEX.note`).
  - An entry's Edit/Remove buttons read `Edit`/`Remove` with the entry's legend in `aria-label`, where they previously
    typed the legend into the visible label. The legend is now the admin's own text, and at 390px a long name wrapped
    one button's label over three lines (seen in the first capture round). The visible word stays contained in the
    accessible name, so the control is still uniquely named (`FEATURES.yaml` `F-CONFIG-SEARCHING.selectors`).
  - `SearchingConfigTab` no longer takes a `transport` prop, because the only consumer of it on that tab was the
    section that moved. Mechanical; no registry anchor.
  - `configFormState.test.ts`'s `should cover every canonical tab exactly once` no longer asserts a bijection between
    `CONFIG_SECTION_TABS` keys and `CONFIG_TABS` paths. It now asserts both halves separately: every section key reaches
    a real tab, and exactly one tab has no section mapping to it — pinned by name as `"customMappings"`, so a *second*
    section-less tab (which would silently badge nothing) still fails. `configFormState.ts`, `CONFIG_SECTION_TABS` and
    `configTabForSectionKey` are unchanged, and a mapping edit still badges Searching. Authorized by the refined packet
    (Acceptance's last bullet and the `Files Allowed To Modify` line naming this file); no registry anchor, since it
    documents no behaviour change.
