## Dependency Notes

First packet of the ADR-0008 structural-redesign batch (FM-039 through FM-042), which adapts the layout ideas of the owner-authored search mock to the existing ADR-0007 theme. It is dependency-free and starts the batch because every later
packet in the batch places a control relative to the results column this task reshapes, and because all four own `core/ui-react/src/features/search/results/SearchResults.tsx`, so they cannot run concurrently (README, Parallel Work). It
builds on FM-034, which established the inline per-column-header filters, the 1700px page container, and the memoized row rendering that this task must not regress.

## Outcome

Result filtering is available from a persistent, collapsible "Refine" sidebar beside the results table — quality chips, title text, collapsible category and indexer lists showing per-item result counts, size/age/grabs ranges, a
download-type chip group, and a single "Clear all" action — bound to the same filter state the existing inline column-header filters already drive.

## Boundary Rationale

One user-observable capability delivered in one place: a new filter surface is worthless without the state, the counts, the new type dimension, and the clear-all reset it presents, and none of those is reviewable without the surface. It is
separate from FM-040 because bulk selection and download actions are a different product capability on different feature records with their own accepted contracts, and separate from FM-041 because display preferences change how rows read,
not what is filtered. The sidebar is feature-scoped under `features/search/results` and already covered by `C-RESULT-TABLE`, so per README's Registry Rules no new `COMPONENTS.yaml` record is required.

### Assumptions

- **`results-quick-filters` visibility split.** The mock's Quality section and FM-034's existing toolbar quick-filter row would otherwise render the same accessible-name buttons (e.g. "WEB", "x265") simultaneously visible at the same viewport, which breaks exact-name Playwright/RTL locators. Resolved by keeping the toolbar row exclusively for `xs` (mobile, matching the existing `results-filters` mobile-only pattern byte-for-byte) and rendering Quality exclusively inside the sidebar at `sm` and up; `filters.quickFilters` is the single shared state either way. This is a task-local UI-composition decision, not an architectural one.
- **Sidebar default-collapsed state and its jsdom fallback.** The sidebar defaults expanded at `sm` and up, collapsed below `sm`, detected via `window.matchMedia("(min-width: 600px)")` at mount (mirroring `theme.ts`'s existing `systemPrefersDark()` defensive-guard pattern) — a stored user preference always wins. When `matchMedia` cannot positively confirm desktop width (unavailable in this project's jsdom component-test environment specifically, not just when genuinely narrow), the default conservatively falls back to **collapsed** rather than assuming desktop. This was a deliberate choice, not an oversight: jsdom always reports a "desktop-sized" `window.innerWidth`, so a "detect narrow, else assume wide" default would make the sidebar's Quality/Type sections render by default in every component test, colliding with the toolbar's own quick-filter buttons (same accessible names) in jsdom specifically, since jsdom does not evaluate the CSS media queries that keep them mutually exclusive in a real browser. Falling back to collapsed-by-default avoids this collision without any jsdom-specific test code, and is verified correct in a real browser via the Playwright evidence above (expanded at 1280px, collapsed at 390px).
- **`window.localStorage` is unavailable in this project's Vitest+jsdom setup.** Diagnosed directly (not assumed): `typeof window.localStorage === "undefined"` throughout every test in this file, because `core/ui-react/vite.config.ts`'s jsdom environment has no explicit `url` option, so jsdom resolves an opaque origin under which the Storage API throws/is disabled by spec. This is a pre-existing, project-wide test-environment characteristic (confirmed unrelated to this task's app code: the exact same `SearchResults.tsx` code round-trips `sidebarCollapsed` correctly once a working `Storage` is stubbed in). `SearchResults.tsx` itself needed no change — `getStorage()`'s existing defensive `try/catch` already handles this exactly as it already had to for the pre-existing sorting/filters persistence.
