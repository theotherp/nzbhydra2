## Outcome

`settingsIndex.ts` (1059 lines, 146 entries) hand-copies the `label` and help of every indexed setting out of the tab JSX,
which its own doc comment (`:4-21`) records as unavoidable "because the tabs define their fields as JSX, not as data".
The copies can silently disagree: `settingsIndexDrift.test.tsx` compares `config-setting-*` ids only, so a wrong label or
stale help string in the index is caught by nothing, and `CSRF_HELP` (`main/mainSettings.ts:110`) exists as a one-off
shared constant precisely to stop that drift for a single string. This task inverts the dependency: the index declares
label and help once and the tabs read from it, so search, the review-changes panel and the feedback banner quote what the
user sees by construction. Behaviour-preserving — identical labels, help, links, order, search results. Backlog item 29.

## Decision Dependencies

ADR-0002 (a typed field vocabulary, not a schema framework — the tabs stay JSX), ADR-0024 (tooltips stay separate from
help), ADR-0039 (search hides matches whose render condition is unmet), ADR-0014.

## Handoff / Review

### Outcome

- `settingsIndex.ts` now *declares* the label and help of every setting the eight tabs render directly, and each of
  those controls reads them back with `{...indexedSetting("<config path>")}`. Nothing states an indexed label or help
  string twice: the tab JSX no longer carries one, and `helpText` — the flat string
  `settingsSearchMatching.ts` runs its substring over — is derived from the very `HelpContent` the control renders by
  `flattenHelp()`, not transcribed beside it.
- `SettingsIndexEntry` gains `help: HelpContent | undefined`, the structured value: links keep their `href`, so
  `SettingHelp` still hands `C-EXTERNAL-LINKS` a link rather than the prose the index used to flatten by hand. The
  entries whose help carries a link are `main.host`, `main.urlBase`, `main.sslKeyStore`, `main.verifySsl`,
  `main.sniDisabledFor`, `main.useCsrf`, `main.databaseRetentionTime`, `main.databaseWriteDelay`, `main.xmx`,
  `searching.globalCacheTimeMinutes`, `notificationConfig.appriseApiUrl` and `notificationConfig.appriseCliPath`; the
  index imports their URL constants (`REVERSE_PROXY_WIKI`, `SSL_WIKI`, `SSL_VERIFICATION_WIKI`, `CSRF_WIKI`,
  `H2_RETENTION_TIME`, `H2_WRITE_DELAY`, `MEMORY_WIKI`, `CACHED_QUERIES_WIKI`, `APPRISE_API_URL`, `APPRISE_CLI_URL`)
  from the same per-tab settings modules the tabs did, none of which is modified.
- `indexedSetting(path)` is the one lookup helper: a `Map` over `SETTINGS_INDEX` keyed by path, returning
  `Pick<SettingProps, "help" | "label" | "name">` and throwing for an unindexed path. `SettingProps.label` stays
  required and `HelpContent` keeps its shape — no control learned to look anything up, so dialog-internal and
  per-entry fields keep their literals and are untouched.
- **Every string difference found: none.** The packet asks for the drift to be reported, so it is reported as measured.
  Before changing anything, each tab's JSX was parsed with the TypeScript AST and the `label` plus the flattened `help`
  of every control compared against the base index's `label`/`helpText`. All indexed rows matched on both fields, no
  indexed row was missing from the JSX, and no labelled JSX control was missing from the index. Consequently the
  ordered `SETTINGS_INDEX` dump is byte-identical before and after (`b1b1d5babbf6491188bdb4d1ad611da4`), with no
  permitted-difference entries to name.
- `settingsIndexDrift.test.tsx` gains direction (d): for every non-conditional row, the rendered row's label and help
  text, read from the DOM, equal the index's. The label is read as the control's accessible name — `aria-labelledby`
  where MUI uses it (a `select`, whose `role="combobox"` may not be wrapped in a `<label>`), the row's `<label>`
  otherwise — with `aria-hidden` decoration (MUI's required asterisk) dropped, so no internal MUI class is named
  (ADR-0014). The help is the node carrying `settingHelpId(path)`, the id `aria-describedby` points at, read as
  `textContent` so a link inlines exactly the way `flattenHelp` does. A volume pin keeps it from going vacuous.
- What direction (d) can and cannot catch, measured rather than asserted: in an isolated mutant tree, changing a
  control back to a literal (`searching.minSeeders` given `label="Minimum seeders"` and no `help`) fails it on both
  fields by name, while editing a string *in the index* does not fail it — because the row now renders that edit too.
  That is the intended consequence of the inversion, and the test's comment says so rather than implying a guard it
  no longer provides.
- Measured, against the packet's prose: the base index holds 141 entries (134 rows + 7 sections) in 1059 lines, not the
  146 the Outcome section states. Nothing depends on the number; it is recorded so the reviewer does not hunt for five
  missing entries.

### Decisions, Assumptions, Debt

- Dependency additions/changes: none.
- Assumption from repository evidence: an index entry's `help` is now a module-level constant rather than an array
  literal rebuilt on every render, so its identity is stable across renders. Nothing memoizes on it — `SettingRow`,
  `SettingHelp` and the control kinds are none of them wrapped in `memo` — and the rendered bytes are identical, so
  this is an improvement in allocation and inert in behaviour.
- Assumption from repository evidence: reading a select's label through `aria-labelledby` is what MUI actually emits
  (`aria-labelledby="…-label"` on the `role="combobox"` node, verified in the captured DOM), not an inference from
  MUI's documentation.
- Temporary workarounds: none.
- Deliberate deviations from the packet, each also recorded in the registry entry named:
  - `main/mainSettings.ts`'s `CSRF_HELP` now has one importer instead of the two the Out Of Scope bullet names,
    because a tab that reads its help from the index cannot also import the constant without lint failing on an
    unused import. The file itself is byte-unchanged. Recorded in `COMPONENTS.yaml` `C-CONFIG-SETTINGS-INDEX`'s note.
  - `COMPONENTS.yaml`'s `C-CONFIG-SETTINGS-INDEX` `responsibility` field was edited alongside its `note`, which the
    allowlist's parenthetical ("`C-CONFIG-SETTINGS-INDEX` note") reads narrowly. Leaving it would have left the
    registry asserting that the index "hand-maintains" copies of the labels — the exact thing this task removed. The
    edit stays inside that one record.
- Debt: none introduced. Direction (d)'s label reader is the one piece of DOM-shape knowledge added, and it is
  expressed as the accessible-name rule rather than as MUI markup, so a control kind that changes its internals keeps
  passing as long as it still names itself to a screen reader.
