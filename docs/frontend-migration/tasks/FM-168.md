# FM-168: Confine An Indexer Keystroke To Its Own Row

Status: planned Owner:
Feature IDs: F-CONFIG-INDEXERS
Component IDs: C-CONFIG-FIELDS
API IDs: None
Depends on: None
Blocks: None

## Outcome

Typing in an indexer's inline cell stops re-rendering the whole indexer list. `IndexersConfigTab.tsx:87` subscribes the
tab to the entire array — `useWatch<ConfigValues>({name: INDEXERS_PATH})` — so every keystroke in any cell re-renders
the tab, `IndexerTable`, and all of its rows; `IndexerTableRow` (`IndexerTable.tsx:379-558`) is a plain function
component with no `memo`, and each row expands to roughly 28 elements before `SelectSetting`, `NumberSetting`, and
`IndexerStateSwitch` unfold their own MUI and React Hook Form subtrees. At the 30-60 indexers real installations carry,
one character costs thousands of component renders. The subscription and the row identity are one problem: memoizing
rows fed by a whole-array watch changes nothing, and narrowing the watch without stable rows changes nothing either.

## Acceptance

- Typing one character into one row's inline cell re-renders that row and nothing else: a new `IndexerTable.test.tsx`
  mounts a table of at least ten indexers with a per-row render counter, types into one cell, and asserts every other
  row's counter is unchanged and the edited row's rose by a bounded amount. The test is demonstrated red against the
  current implementation and green after.
- The tab's whole-array subscription is narrowed to what the tab and table actually need outside the rows (identity,
  order, and any value the header or bulk controls read); per-field values are subscribed inside the row that renders
  them. `IndexerTableRow` is memoized and every prop it receives is referentially stable across an unrelated row's
  edit.
- The frozen-order invariant is preserved literally: `frozenOrder` remains only ever a permutation of the live rows,
  entries are still re-read from the form on every render so no value is ever stale, the freeze is still dropped when
  the entry count changes or a held index stops resolving, and a header click still clears it. A test drives the
  documented sequence — focus a cell, edit a value that would change the sort, confirm the order holds, blur, confirm
  it resorts.
- Every existing assertion in `IndexersConfigTab.test.tsx` stays green unmodified; if one must change, the handoff
  names it and says why the new form asserts at least as much.
- Editing, adding, deleting, bulk enable/disable, filtering, and the colour setting behave exactly as today, including
  ADR-0040's search-source gating.
- No rendering change, so no screenshot strip is required beyond one desktop 1280x800 capture of the indexer table with
  a cell focused, confirming the visual result is unchanged.

Implementer prompt: Start with `IndexerTable.tsx:118-155` and treat its doc comment as the specification — the freeze
