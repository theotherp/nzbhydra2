# FM-040: Selection-Gated Bulk Actions Bar And Header Selection Menu

Status: done Owner: migration-implementer Feature IDs: F-SEARCH-GROUP-SELECTION, F-SEARCH-DOWNLOADS, F-SEARCH-SAVED, F-SEARCH-RESULTS Component IDs: C-RESULT-TABLE, C-DOWNLOAD-ACTIONS API IDs: None Depends on: FM-039 Blocks: FM-041

## Dependency Notes

Second packet of the ADR-0008 structural-redesign batch. It depends on FM-039 for two reasons: both own `SearchResults.tsx`, which README's Parallel Work rules forbid two concurrent tasks from owning, and this task's geometry contract
places the bulk-actions bar relative to the results column whose width FM-039 changes, so evidencing it before the sidebar exists would produce a baseline that FM-039 immediately invalidates. It blocks FM-041, which adds a further control to
the toolbar this task restructures.

## Outcome

Row selection and its two primary bulk actions are presented the way the mock arranges them: a tri-state select-all checkbox with a Select all / Deselect all / Invert selection menu in the results table header, and a bar showing the
filtered/loaded/selected counts alongside "Send to downloader" and the NZB ZIP download, both visibly disabled until rows are selected — replacing the current flat row of selection buttons without dropping any existing download capability.

## Boundary Rationale

Selection affordances and the actions they gate are one reviewable capability: moving selection into the table header only makes sense together with the bar that reports and consumes the selection, and the disabled-until-selected behavior
is meaningless without both. It is separate from FM-039 because filtering and selection are different capabilities on different feature records, and separate from FM-041 because display preferences do not change what selection or download
actions do. It carries three accepted `FEATURES.yaml` records whose accepted geometry checks describe exactly the toolbar regions it restructures, so their re-proposal must land in the same change.

## Acceptance

  presence. The caret exposes `aria-haspopup="menu"` and `aria-expanded`, and each entry is a `role="menuitem"` with a distinct accessible name.
- The three toolbar selection buttons are removed, and the `results-selection-actions` `data-testid` stays on whichever region now carries the selection affordances, so the existing selector contract and the record's geometry check keep a
  real target. Below `sm` the responsive table styling hides `thead`, so the selection menu must remain reachable in the toolbar at mobile; a test asserts this rather than assuming it.

  an addition, with its own `data-testid` if rendered separately.

### Outcome

Row selection and its two primary bulk actions now match the mock's arrangement, adapted to the current ADR-0007 theme (ADR-0008 Option B: structure only). The results table header's Select cell (`core/ui-react/src/features/search/results/SearchResults.tsx`, new local `SelectionMenu` component) renders a real tri-state checkbox — `checked` when every currently visible row is selected, `indeterminate` on a partial selection, unchecked when none is — plus an adjacent caret (`aria-haspopup="menu"`, `aria-expanded`) opening a MUI `Menu` (`role="menu"`) with `Select all` / `Deselect all` / `Invert selection` `menuitem`s, each producing exactly the same `selectVisibleResults` outcome the old flat toolbar buttons produced. Because the responsive table hides `thead` entirely below `sm`, a second, functionally-identical copy of the same `SelectionMenu` (same state/callbacks, distinct `idPrefix="toolbar"`) renders inside the toolbar's `results-selection-actions` region, visible only at `xs`, so bulk selection stays reachable at mobile — asserted by a dedicated Playwright interaction, not assumed. `results-selection-actions` keeps its `data-testid` and now carries the grouping toggles (unchanged) plus that mobile-reachable menu copy.

A new `results-bulk-actions` bar (`DownloadActions.tsx`, restructured) reports the loaded/filtered counts (`results-bulk-actions-summary`, e.g. "2 of 2 loaded results") and, once non-zero, the selected count (`results-selected-count`, its own `data-testid` per the packet's instruction), alongside the bar's two primary actions: "Send to downloader" (`send-to-downloader`, unchanged text/testid) and the NZB ZIP download ("Download selected NZBs as ZIP", unchanged text). Both are now `disabled` (MUI's native `disabled` attribute, not opacity/toast) until at least one result is selected, replacing the prior behavior where "Send to downloader" fired unconditionally and NZB ZIP relied on an equivalent but narrower `selectedNzbs.length === 0` gate. Every other existing bulk capability — downloader select, downloader-category select, black-hole/save action, copy-links action, and Save search — remains present, reachable, and behaviorally unchanged, now grouped together in one labeled `results-download-actions` region (Save search moved in from being a sibling in `SearchResults.tsx` to being rendered by `DownloadActions` itself, guarded by the exact same dialogs/toasts-availability condition, with an un-gated fallback preserving today's behavior in the theoretical case that guard is false; see Assumptions). `core/ui-react/src/domain/downloads/**` is unmodified; `C-DOWNLOAD-ACTIONS`'s request/response contracts are unchanged.

### Assumptions

- **`assertGroupExpansionAndBulkSelection` (pre-existing, shared Playwright helper) needed updating beyond "this task's own visual-evidence block."** This task's `Files Allowed To Modify` for `results.spec.ts` reads "only this task's visual-evidence block," mirroring FM-039's precedent.
