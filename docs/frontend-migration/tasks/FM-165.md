# FM-165: Put History Filter, Sort, And Page In The URL

Status: planned Owner:
Feature IDs: F-HISTORY-SEARCHES, F-HISTORY-DOWNLOADS, F-HISTORY-NOTIFICATIONS
Component IDs: None
API IDs: None
Depends on: None

## Outcome

A filtered, sorted, paged history view becomes a link: shareable, bookmarkable, and restored by Back. None of the three
pages puts anything in the URL today — `useHistoryFilterCriteria.ts:41-99` holds page and filter values in component
state, each page holds `sort` in its own `useState` (`SearchHistoryPage.tsx:75`, `DownloadHistoryPage.tsx:67`,
`NotificationHistoryPage.tsx:56`), and `validateSearch` appears nowhere in `src/`. So "Repeat" from search history, or
any external navigation followed by Back, drops the whole view. All three pages share one hook and one route factory
(`features/stats/routes.tsx:54-58,67,73,76`), so the mechanism is built once and adopted three times here; splitting by
page would mean designing the same schema three times.

## Acceptance

- Each of the three routes declares `validateSearch` over one shared Zod schema covering page, sort field and
  direction, and the committed filter values. A pristine view has a clean URL: every parameter at its default is
  omitted, so today's links keep working and the empty page looks unchanged.
- The schema is total, never throwing: an unknown, malformed, or out-of-range parameter (a stale bookmark, a hand-typed
  URL, a dimension that no longer exists) falls back to that parameter's default and the page renders — no error
  boundary, no 404.
- `useHistoryFilterCriteria` derives `criteria` from the route's search params instead of local state and keeps its
  external contract (`clearFilters`, `commitFilters`, `criteria`, `goToPage`, `updateFilter`, `values`), so the pages'
  query keys and request payloads are byte-identical for the same inputs.
- The 275ms debounce is preserved and now also protects the history stack: debounced `updateFilter` commits navigate
  with `replace`, so typing leaves one entry rather than one per keystroke, while `goToPage`, sort changes, and
  `clearFilters`/`commitFilters` push. `goToPage` still flushes a pending draft first.
- Sort moves out of each page's `useState` into the URL with its current default and toggle behavior; the sort model
  sent to the backend is unchanged (pinned by `notification-history.spec.ts`'s sort assertion).
- Round trip is proven per page: set a filter, a sort, and a page; read the URL; mount a fresh page at that URL and get
  the same rendered state and request payload. One test proves Back after navigating away restores that view.
- The three page suites render under `createHydraTheme` (they wrap only `QueryClientProvider` today), discharging that
  part of the standing follow-up candidate while their harnesses are being rewritten anyway.
- The three system specs keep every existing assertion — the refine `filterModel` payloads, ADR-0016's empty-selection
  `{}`, the `notification-history-page-status` text — and one additionally reloads on a filtered URL and asserts the
  filtered view comes back.
- Each `F-HISTORY-*` record gains a line recording filter, sort, and page as URL state (a capability legacy lacked).
- Screenshot strip per `../README.md` *Visual Gate*: a filtered, sorted, page-2 search history at 1280x800 with the URL
  bar legible, the same URL after a reload, and 390x844 — the pages are otherwise unchanged.
