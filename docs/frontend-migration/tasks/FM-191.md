## Outcome

Five config list editors carry the same hand-copied modal-transaction machinery FM-064 established: an
`Editing = {index, token, value}` state, a `transactionRef` counter bumped on open, close and delete, and a commit that
drops a resolved transaction whose token is stale or whose index no longer exists. `CustomMappingsSection` has the modal
shape but no `token` field at all (`:39-43`, `:87-102`), so it is the one editor where a stale commit has no guard —
today only because its dialog happens to be synchronous. One `useListEditorTransaction` hook in `features/config/` owns
the lifecycle and the staleness rules for all six; each section keeps its own dialog, array write and confirm step.
Behaviour-preserving. Backlog item 22; one packet because the hook's interface is only readable off all six call sites.

## Acceptance

- `useListEditorTransaction` owns the `{index, token, value}` state, the monotonic token counter, `open`, `close`,
  `cancel`, an `isCurrent(token)` predicate, and a guarded commit that runs the caller's write only when the token is
  current and the index is still in range. The array write, merge vs replace, confirm dialogs, the placeholder add and
  its unmount rollback, and per-section draft fields stay in the call site.
- All six sections use it and hold no `transactionRef` of their own. `CustomMappingsSection` gains the guard by adoption:
  reach for a red-first case in `SearchingConfigTab.test.tsx` through the section's own API; if that state is unreachable
  while `CustomMappingDialog` stays synchronous, say so and let the hook's unit test carry the proof — never make it
  reachable by changing the dialog.
- Every existing case in the six suites keeps its assertions — the FM-064 stale-check cases
  (`DownloadingConfigTab.test.tsx` from `:467`, `ExternalToolsConfigTab.test.tsx` from `:837`) and FM-119's abandoned-add
  and blank-name cases included. Only imports, helper names and the new case may change; a changed assertion is a
  required finding. Every `data-testid` survives unchanged, and entries stay bound to the config array index.
- The hook's own unit test covers: a stale-token commit is dropped; a commit whose index no longer exists is dropped; a
  delete makes an open transaction on a later row stale; a fresh transaction after a close commits.
- No screenshot strip: no rendering changes. Instead, for one section per merge strategy (`AuthUsersSection` and
  `IndexersConfigTab`), capture the section's `outerHTML` at base and after and show the pair byte-identical.

### Decisions, Assumptions, Debt

- Dependency changes: none.
- The hook takes the index-range guard as an optional `entryCount` on the commit request rather than owning it, because
  imposing it on the three sections that never had it would convert a commit over a removed row from an unchanged-array
  write (which still marks the form dirty) into a silent no-op. That is the packet's "two divergences the hook must not
  erase", and a unit case pins the no-`entryCount` behaviour so a later tidy-up cannot quietly unify them.
- The hook is generic in three parameters — the draft value, an `Extra` for per-section fields (`CategoriesTable`'s
  `isNew`, `IndexersConfigTab`'s preset `info`), and the index type, so `CategoriesTable` keeps its non-nullable
  `number` index and its `onDelete` needs no narrowing. One `as` cast, commented, spreads the generic `Extra`.
- `commit` returns whether the write ran; `AuthUsersSection` and `CategoriesTable` key their focus request on it, which
  is the same condition as before (the focus request followed a successful write in both).
- In `AuthUsersSection`, `CategoriesTable` and `CustomMappingsSection` the current array is read before the token check
  rather than after it, since `entryCount` needs it. `getValues`/`useWatch` reads are pure, so a dropped commit still
  writes nothing; only the ordering of two reads changed.
- Deliberate deviation from previous behaviour, one bullet, and it is `CustomMappingsSection` only: its commit is now
  token-guarded and index-range-guarded, and its `remove` invalidates the open transaction. Before, a delete under an
  open dialog let the submit write the edited mapping onto whichever row shifted into the captured index (reproduced
  above). This is the packet's Acceptance — "`CustomMappingsSection` gains the guard by adoption" — not an unrecorded
  change, so it is registered in this packet and in `COMPONENTS.yaml`'s `C-CONFIG-FORM` note rather than as a
  `FEATURES.yaml` gap: no user-visible capability changed, and nothing an admin can do in a browser today reaches the
  state either way.
- Reachability, as the Acceptance asks to be told plainly: while `CustomMappingDialog` stays synchronous, no *browser*
  interaction can open the window the guard closes — MUI's backdrop covers the row's Remove button, and the dialog's
  submit has no `await` between the click and `onSubmit`. The new case drives that interleaving through the section's
  own API in jsdom; the hook's unit cases carry the rest of the proof. The dialog was not changed to make anything
  reachable.
- Debt: none introduced.
